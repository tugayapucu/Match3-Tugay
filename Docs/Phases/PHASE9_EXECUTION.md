# Phase 9 Execution Plan — Scoring, Moves, Goals, Win/Lose, Restart

Phase 9 turns the current Match-3 prototype into one small playable level.

Example:

```text
Moves: 20
Goal: collect 25 Red tiles
Score: 0
```

The level ends when:

```text
goal reached → Win
moves reach 0 before goal → Lose
```

A valid player swap consumes exactly one move. An invalid swap consumes no move. All tiles cleared by a valid move, including cascades, contribute to score and goal progress.

This phase also adds a minimal HUD and restart flow.

The phase must remain small and understandable. Prefer a few cohesive classes and explicit data flow over frameworks.

---

# Phase 9 Gameplay Rules

Unless Step 1 finds a concrete reason to change them, use these rules.

## Moves

```text
starting moves: configurable
valid player swap: -1 move
invalid swap: 0 moves
cascade round: 0 additional moves
```

One player action costs at most one move.

## Score

Use the simplest useful rule:

```text
score = cleared tile count × points per tile
```

`pointsPerTile` should be configurable.

Suggested default:

```text
100 points per cleared tile
```

No combo/cascade multiplier in Phase 9.

A cascade scores because it clears tiles, not because it has a separate multiplier.

## Collection Goal

One configurable goal:

```text
GoalTileType
GoalTarget
```

Example:

```text
Red
25
```

Every cleared tile of that type counts, including cascades.

Do not count:

```text
tiles merely moved
tiles swapped but not cleared
tiles generated by refill
invalid swaps
```

## Win / Lose

Use a separate level-status concept:

```text
Playing
Won
Lost
```

After a valid move finishes resolving:

```text
if goal reached:
    Won
else if moves remaining == 0:
    Lost
else:
    Playing
```

**Win has priority over Lose on the last move.**

Example:

```text
Moves remaining before move: 1
Goal progress: 23 / 25
Move clears 2 Red

After move:
Moves = 0
Goal = 25 / 25
Status = Won
```

## Terminal Input

When status becomes:

```text
Won
Lost
```

the player must not be able to start another board move.

This is **level outcome**, not the Phase 8 interaction lock.

Do not merge these concepts merely because both can block input.

## Restart

Restart should reset:

```text
board
moves
score
goal progress
level status
selection/input availability
HUD
```

Keep restart simple.

Phase 9 does not need arbitrary restart during a running animation.

Prefer restart from a settled terminal state unless Step 1 finds a strong reason otherwise.

# Communication Principle

The new systems need facts, not hidden dependencies.

Conceptually:

```text
BoardResolutionRunner
        ↓
"these tile types were cleared by this valid move"
        ↓
BoardInputController / level integration
        ↓
LevelProgress
        ↓
LevelController
        ↓
HUD
```

Possible mechanisms:

```text
direct method call
small injected callback
one local C# event
```

All are acceptable if they keep ownership clear.

Do **not** build:

```text
global EventBus
EventManager singleton
string-based events
generic message broker
reflection-driven observer system
```

for one level.

# Important Result Contract

Scoring and goal tracking need to know what was actually cleared.

Today, after a cell becomes `Empty`, its previous `TileType` is gone.

Therefore Phase 9 needs a small result contract somewhere in the resolution flow.

The minimum useful information is:

```text
which TileTypes were cleared during the full resolution
```

Potential shapes include:

```csharp
IReadOnlyList<TileType>
```

or:

```text
ResolutionResult
├── cleared tile types/counts
└── optional round count if already useful
```

Do not add position data, combo metadata, special-tile metadata, or scoring rules unless current requirements need them.

The result reports facts.

It must **not** calculate score or decide Win/Lose.

# Step 3 — Report Resolution Results

## Goal

Do not add scoring or UI here.

## Result Contract

Implement the approved Step 1 result shape.

It must be:

```text

Core-type-only
independent from UI
independent from scoring rules
```

At minimum it must allow the caller to answer:

```text
How many tiles were cleared?
How many cleared tiles were Red?
```

No combo multiplier.

No goal logic.

No score calculation.

## Resolution Timing

For every resolution round:

```text
FindMatches
    ↓
capture TileType for each matched position
    ↓
ClearCells
    ↓
visual clear
    ↓
gravity
    ↓
refill
```

The tile type must be captured **before** clearing makes the cell `Empty`.

Intersections must count a cell once, consistent with MatchFinder's deduplicated positions.

Aggregate all rounds into one result for the player move unless Step 1 explicitly approved another design.

## Required Tests

At minimum:

- one match reports exact cleared types
- multiple simultaneous matches report all unique cleared cells
- intersection center counted once
- two cascade rounds aggregate both rounds
- three cascade rounds aggregate all rounds
- refill-created match contributes to the same player-move result
- result contains no Empty values
- final board behavior is unchanged
- same deterministic input gives same result

Existing Phase 7 resolution tests must continue passing.

## Presentation Boundary

If `BoardResolutionRunner` produces the aggregate result, it may use Core value types.

Do not make Core depend on the runner.
